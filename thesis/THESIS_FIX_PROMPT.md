## Часть 2. Что НЕ так с текущим .docx (визуальная диагностика)

Перед началом правок ОБЯЗАТЕЛЬНО:
1. Конвертируй `thesis/build/ПЗ_РысаевАИ_ААМ-24-07.docx` в PDF через `python3 "<DOCX_SKILL>/scripts/office/soffice.py" --headless --convert-to pdf …` и далее в PNG: `pdftoppm -jpeg -r 150 …` (см. инструкции skill `anthropic-skills:docx`).
2. Просмотри первые 10 страниц через Read tool (pages: "1-10").
3. Зафиксируй в `thesis/build/diagnostics.md` конкретный список визуальных дефектов: разъехавшиеся таблицы, читаемость подписей, неверные межстрочные интервалы, отсутствие подписей под рисунками, выравнивание заголовков, нумерация страниц.

**Известные дефекты, на которые точно надо обратить внимание:**
- В Приложении А вместо реального кода стоят литерально `{{INCLUDE_FILE: путь_к_файлу}}` — это плейсхолдеры, их надо подменить содержимым файлов.
- В тексте глав 1–4 + приложений Б есть маркеры `[РИСУНОК N.M: описание]` и `[ТАБЛИЦА N.M: …]` — рисунков физически нет, нужно сгенерировать PNG-диаграммы (Mermaid/PlantUML/draw.io) и вставить в .docx как `<w:drawing>` с подписью под рисунком.
- Pandoc склеивает Markdown-таблицы в Word-таблицы без задания ширины — некоторые широкие таблицы вылезают за поля. Нужно проверить и при необходимости задать `columnWidths` или повернуть на 90° (для крупных).
- В Главе 5 (ТЭО) формулы записаны inline в Markdown, нужно проверить, что они корректно отображаются (либо переоформить как блочные с нумерацией).
- В Главе 1 списки требований могут выглядеть как «голые точки» — у pandoc нет единой нумерации стилей; нужно унифицировать (либо нумерованные, либо маркированные с `LevelFormat.BULLET`).
- В заголовках кое-где остался `#` или `**` Markdown-разметка (особенно после правок) — поискать и убрать.
- В Содержании (TOC) может быть пустое поле — pandoc вставляет `\toc` placeholder, который заполняется только при открытии в Word и нажатии F9.
- Шрифт заголовков 1/2/3 уровня — pandoc по умолчанию использует тематический Calibri, нужно подменить на Times New Roman (как и Normal style).

## Часть 3. ГОСТ-форматирование — какие правки обязательны

### 3.1. Параметры страницы
- Формат A4 (11906 × 16838 DXA), ориентация книжная.
- Поля: верх 2 см (1134 DXA), низ 2 см (1134), левое 2,5 см (1418), правое 1 см (567).
- 1 см = 567 DXA.

### 3.2. Основной шрифт
- Times New Roman 14 пт (sz=28 в half-points), цвет автоматический.
- В крупных таблицах допустимо TNR 12 пт (sz=24), межстрочный 1,15 или 1,0.
- В коде/листингах — Consolas или Courier New 10 пт (sz=20), межстрочный одинарный.

### 3.3. Абзац
- Выравнивание основного текста — по ширине.
- Отступ слева 0, справа 0, первая строка 1,25 см (708 DXA).
- Интервал перед/после — 0 пт; междустрочный — 1,5 (line="360" lineRule="auto").

### 3.4. Заголовки
- Стили Word «Заголовок 1», «Заголовок 2», «Заголовок 3» — обязательно с `outlineLevel`, чтобы TOC собрался.
- Все заголовки — Times New Roman, прописными для уровня 1 (например, «ГЛАВА 1. АНАЛИТИЧЕСКИЙ ОБЗОР ПРЕДМЕТНОЙ ОБЛАСТИ»), смешанными для уровня 2 и 3.
- Выравнивание по центру (для уровня 1 и Введения/Заключения/Литературы); для уровня 2 — слева с отступа абзаца.
- Точка в конце заголовка не ставится. Перенос слов в заголовках запрещён.
- Каждый раздел уровня 1 — с НОВОЙ страницы (PageBreak).

### 3.5. Нумерация страниц
- Правый нижний угол, арабские цифры.
- Сквозная: титульный лист — страница 1, но номер на нём не виден (включить «особый колонтитул первой страницы»).
- Номера видимы начиная с Введения (или с Аннотации, по факту первой нумеруемой).

### 3.6. Содержание
- Автособираемое поле TOC (вставляется через `\toc` в pandoc, открывается и обновляется в Word через Ctrl+A → F9).
- Глубина 3 уровня заголовков.

### 3.7. Таблицы
- Подпись СВЕРХУ по центру: «Таблица N.M Название» (без точки в конце, без двоеточия). Шрифт подписи — TNR 14 пт.
- Сквозная нумерация по работе ИЛИ по разделу (выбран «по разделу»: «Таблица 1.1», «Таблица 1.2», «Таблица 2.1» и т. д.).
- Ширина не более текстового поля (9026 DXA при A4 + полях 2,5/1).
- При переносе шапка дублируется (`<w:tblHeader/>` в `<w:trPr>` первой строки).
- Большие таблицы — TNR 12 пт, интервал 1,15.
- Все таблицы должны быть упомянуты в тексте ДО самой таблицы фразой «В таблице N.M …».

### 3.8. Рисунки
- Подпись СНИЗУ по центру: «Рисунок N.M Название» (без точки). Шрифт TNR 14 пт.
- Сквозная нумерация по разделу.
- Все рисунки должны быть упомянуты в тексте ДО самого рисунка фразой «На рисунке N.M …».

### 3.9. Формулы
- Сквозная нумерация в круглых скобках справа на уровне формулы.
- После формулы — «где» без двоеточия, пояснения с новой строки.

### 3.10. Ссылки на источники
- `[N]` или `[N, c. M]` перед знаком препинания (перед точкой, запятой, точкой с запятой, тире, двоеточием).
- Все 38 источников из списка литературы должны быть упомянуты в тексте хотя бы 1 раз.

### 3.11. Списки
- Маркированные — через `LevelFormat.BULLET` в numbering.xml, НЕ unicode-точками.
- Нумерованные — через `LevelFormat.DECIMAL`.
- В местах связного изложения списки заменять на текст.

## Часть 6. Замена плейсхолдеров листингов в Приложении А

В `thesis/build/draft/09_appendix_A.md` 9 листингов вида:

```
### Листинг А.1 — `DockerSandboxService.kt`

\`\`\`kotlin
{{INCLUDE_FILE: sandbox/src/main/kotlin/ru/sandbox/service/DockerSandboxService.kt}}
\`\`\`
```

Эти `{{INCLUDE_FILE: …}}` нужно подменить РЕАЛЬНЫМ содержимым файлов. Сделай это через bash-скрипт на этапе пересборки `full.md`:

```bash
python3 - <<'PY'
import re, pathlib
src = pathlib.Path("thesis/build/draft/09_appendix_A.md").read_text(encoding="utf-8")
def inject(match):
    path = match.group(1).strip()
    code = pathlib.Path(path).read_text(encoding="utf-8")
    return code
result = re.sub(r"\{\{INCLUDE_FILE:\s*([^}]+)\}\}", inject, src)
pathlib.Path("thesis/build/draft/09_appendix_A_full.md").write_text(result, encoding="utf-8")
PY
```

Затем в `full.md` подключи `09_appendix_A_full.md` вместо placeholder-варианта.

**Оформление листингов в .docx:**
- Шрифт Consolas 10 пт (или Courier New).
- Межстрочный одинарный.
- Без переноса слов, по левому краю.
- Нумерация строк через `<w:lnNumType w:countBy="1" w:start="1"/>` в `<w:sectPr>` ИЛИ через ручной префикс «01 », «02 » в начале каждой строки.
- Заголовок «Листинг А.N — `<имя файла>`» — TNR 12 пт, по центру, перед листингом.

## Часть 7. Усиление главы 2 — описание и обоснование архитектуры

Босс конкретно сказал «добавь описание архитектуры обоснование». Перепиши разделы 2.1–2.8 главы 2 так, чтобы каждое архитектурное решение сопровождалось ОБОСНОВАНИЕМ в формате:

> «Решение: <что>. Альтернативы: <что ещё рассматривалось>. Обоснование выбора: <почему именно это>. Trade-offs: <чем пришлось пожертвовать>.»

**Конкретно нужно обосновать:**

1. **Выбор Kotlin вместо Java/Python для backend.**
   Альтернативы: Java 21, Python (Django/FastAPI), TypeScript (Node.js).
   Обоснование: null-safety, краткость синтаксиса, JVM-совместимость с экосистемой Spring, `data class` для DTO без boilerplate, `plugin.jpa` + `allOpen` решает проблему `final` без аннотаций.
   Trade-offs: меньше готовых JPA-примеров чем у Java, кривая обучения для тех, кто пришёл из Java.

2. **Выбор Spring Boot 3.5 вместо Ktor/Micronaut/Quarkus.**
   Альтернативы: Ktor (родной для Kotlin), Micronaut (быстрый запуск), Quarkus (native через GraalVM).
   Обоснование: широкая поддержка, мощная экосистема Spring Security/Data JPA/Kafka, готовые стартеры actuator + prometheus, опыт автора.
   Trade-offs: больший cold start, больший образ Docker.

3. **Выбор PostgreSQL вместо MySQL/MongoDB.**
   Альтернативы: MySQL, MongoDB, SQLite.
   Обоснование: ACID, JSONB для хранения `arguments`/`tests`/`test_results` без отдельной таблицы тестов, нативный UUID, расширения (pgcrypto), Flyway-совместимость.
   Trade-offs: тяжелее SQLite, требует отдельного контейнера.

4. **Выбор Kafka вместо RabbitMQ/Redis Streams.**
   Альтернативы: RabbitMQ (AMQP), Redis Streams, in-process очередь.
   Обоснование: масштабируемость воркеров через consumer-group, persistence по умолчанию, при необходимости — replay сообщений для отладки sandbox-инцидентов.
   Trade-offs: тяжёлая инфраструктура (Zookeeper + Kafka), сложнее в DevOps.

5. **Выбор Docker host-side вместо Docker-in-Docker / gVisor / nsjail / Firecracker.**
   Альтернативы: DinD (полная изоляция, но требует privileged), gVisor (user-space ядро, медленнее), nsjail (только Linux), Firecracker (микро-ВМ, требует KVM).
   Обоснование выбора Docker host-side: работает на macOS Docker Desktop (важно для разработки и защиты), достаточная изоляция при использовании hardening-флагов (`--cap-drop=ALL`, `--read-only`, `--network=none`, `--no-new-privileges`, `--pids-limit`, `--tmpfs noexec,nosuid,nodev`), быстрый старт контейнера (~150 мс).
   Trade-offs: общий kernel с host'ом, в проде нужен либо отдельный VM-хост, либо переход на gVisor.

6. **Выбор GigaChat вместо OpenAI/Claude/Yandex GPT.**
   Альтернативы: OpenAI GPT-4 (платно, geo-fence для РФ), Claude (платно, geo-fence), Yandex GPT (российский), локальная LLaMA-2/Mistral.
   Обоснование: доступность из РФ без VPN, free-tier через персональный токен, OAuth2 client_credentials.
   Trade-offs: качество ниже чем у GPT-4 на длинных задачах, ограничение rate-limit.

7. **Выбор OpenAPI-first вместо code-first.**
   Альтернативы: springdoc-openapi (code-first), вручную написанные DTO.
   Обоснование: single source of truth для front + back, типобезопасные клиенты на TypeScript, контракт ревьюится отдельно от кода.
   Trade-offs: одна точка отказа (опечатка в YAML ломает билд всех модулей), требуется регенерация при изменениях.

8. **Выбор JWT вместо session-based auth / OAuth2 server.**
   Альтернативы: Spring Session + Redis, OAuth2 authorization server, opaque token.
   Обоснование: stateless (CSRF не нужен), горизонтально масштабируется без shared storage, простая интеграция с фронтом (Bearer-header).
   Trade-offs: нельзя «отозвать» токен до истечения TTL, размер заголовка больше cookie.

9. **Выбор React 18 + Vite 5 + MUI v5 + Monaco вместо Angular/Vue/Next.js.**
   Альтернативы: Angular (тяжелее, opinionated), Vue (меньше готовых компонентов), Next.js (SSR не нужен для образовательного SPA).
   Обоснование: огромная экосистема, hot reload Vite < 100 мс, MUI v5 уже включает темизацию и accessibility, Monaco — фактический стандарт для in-browser code editor.
   Trade-offs: bundle ~5 МБ из-за Monaco, потребуется code-splitting при росте.

10. **Выбор client-side фильтрации задач + сервер-side endpoint `/tasks/categories`.**
    Альтернативы: чисто client-side (без сервера), чисто server-side (RSC), GraphQL.
    Обоснование: для каталога < 1000 задач client-side даёт мгновенную отзывчивость без round-trip; endpoint категорий нужен для UI чипов фильтра без загрузки всех задач.
    Trade-offs: при росте каталога > 1000 задач придётся переходить на server-side фильтрацию (уже подготовлено через `?category=&difficulty=` в GET /tasks).

Каждое обоснование — 1–2 абзаца в основном тексте.

Дополнительно к разделу **2.7 (AI-анализатор)** усилить ОБОСНОВАНИЕ нейро-символьного подхода:
- Почему именно эта иерархия `sandbox > AST > LLM`, а не `LLM > AST > sandbox`? Потому что sandbox — детерминированный источник истины: тест либо прошёл, либо нет. LLM — стохастический, может галлюцинировать. AST — детерминированный, но не отражает поведение, а только структуру.
- Почему verdict-cap=40 при passed=0? Это эмпирический cap: средняя оценка качества «небрежного» кода ~30-40, оценки выше — это уже про работоспособный код. Если ни один тест не прошёл — никакая работоспособность не доказана, оценка не может быть выше 40.
- Почему AST-факты в отдельном блоке промпта, а не вкомпонованы в код? Потому что LLM лучше следует инструкциям, когда контекст структурирован «секционно» с явными разделителями.
