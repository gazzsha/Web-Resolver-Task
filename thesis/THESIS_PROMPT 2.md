# Промпт для написания магистерской диссертации (ДИР)

**Назначение этого файла.** Это исполняемый промпт для отдельной сессии Claude Code. Он самодостаточен: получив его, агент должен (1) прочитать репозиторий, (2) собрать материал по разделам ниже, (3) сгенерировать единый `.docx`-документ в `thesis/build/`, (4) приложить рабочие диаграммы и скриншоты. Промпт построен так, чтобы материал брался из ФАКТИЧЕСКОГО кода и результатов экспериментов, без галлюцинаций.

## Часть 2. Стандарты оформления (жёсткие требования)

Соблюдай в одном документе одновременно:

1. **ГОСТ 7.32-2017** — отчёт о НИР. Это базовый стандарт:
   - шрифт Times New Roman 14 пт (заголовки 14–16 пт);
   - межстрочный интервал 1,5; красная строка 1,25 см;
   - поля: левое 30 мм, правое 15 мм (для подшивки в иных вузах 10–15 мм допустимо), верхнее 20 мм, нижнее 20 мм;
   - нумерация страниц арабскими цифрами сверху по центру, начиная с введения, титульный лист считается, но не нумеруется;
   - выравнивание основного текста — по ширине, переносы автоматические;
   - заголовки разделов прописными, без точки в конце, не подчёркивать, выравнивание по центру;
   - подзаголовки с абзацного отступа, первая буква прописная;
   - таблицы и рисунки — сквозная нумерация по работе или по разделу (выбери «по разделу», как принято на технических кафедрах); подпись таблицы СВЕРХУ слева, рисунка — СНИЗУ по центру;
   - формулы по центру, нумерация в круглых скобках справа.

2. **ГОСТ 2.105-95** — общие требования к текстовым документам:
   - перечисления маркерами «–» или «)»;
   - сокращения через точку «и т. д.», «и т. п.», «см.», «др.», «пр.»;
   - запрет на сокращения внутри предложений, кроме принятых ГОСТом.

3. **ГОСТ 7.0.5-2008** — библиографические ссылки:
   - в тексте — затекстовые ссылки в квадратных скобках `[12]` или `[12, c. 45]`;
   - в списке литературы — соответствующая запись по номеру;
   - список оформляется в порядке появления в тексте (либо по алфавиту — выбери «по алфавиту»).

4. **ГОСТ 7.1-2003** — библиографическое описание:
   - книги: `Фамилия И. О. Название : подзаголовок. — Город : Издательство, Год. — N с. — ISBN ...`;
   - статьи: `Фамилия И. О. Название статьи // Журнал. — Год. — Т. N, № M. — С. K–L.`;
   - электронные ресурсы: `Название [Электронный ресурс]. — URL: ... (дата обращения: ДД.ММ.ГГГГ).`

5. **ГОСТ 19.701-90** — схемы алгоритмов и программ:
   - блоки строго ГОСТовские: «процесс» (прямоугольник), «решение» (ромб), «данные» (параллелограмм), «терминатор» (овал), «соединитель» (круг), «предопределённый процесс» (прямоугольник с двойными вертикальными гранями);
   - стрелки только прямые/ортогональные; запрет на «зигзаги» и круги без подписи.

**Override.** Если автор пришлёт методичку кафедры — она имеет ПРИОРИТЕТ над любым ГОСТом выше. В этом случае подмени поля шрифта/отступов/нумерации из методички, но оставь библиографию по 7.0.5-2008.

## Часть 3. Структура работы

> Соблюдай порядок страниц жёстко. Каждый раздел начинается с НОВОЙ СТРАНИЦЫ.

1. **Титульный лист** (без номера страницы; учитывается в сквозной нумерации).
2. **Задание на ДИР** (отдельный лист по шаблону вуза; если шаблона нет — используй стандартный лист задания с полями: тема, исходные данные, перечень подлежащих разработке вопросов, перечень графического материала, дата выдачи задания, срок сдачи).
3. **Календарный план** (таблица: этап / срок / отметка о выполнении).
4. **Реферат** (1 страница; объём в стр., число иллюстраций, таблиц, использованных источников; ключевые слова прописными через запятую — не более 15; краткая аннотация на 1500–2000 знаков с указанием объекта, предмета, цели, методов, результатов, области применения).
5. **Abstract** (английская версия реферата, 1 страница).
6. **Содержание** (автособираемое из стилей заголовков).
7. **Перечень условных обозначений и сокращений** (если набирается ≥ 5 терминов; обязательно для технической работы — JWT, HTTP, JPA, ОРМ, КЭК и т.п.).
8. **Введение** (4–6 стр.):
   - актуальность темы (рост дистанционного обучения, нехватка преподавателей-кодеров, рутина проверки решений; рынок LeetCode/HackerRank как индикатор спроса);

   - практическая значимость (сервис применим в учебном процессе кафедры информатики, в открытых курсах, в корпоративном обучении);
   - объект исследования (процесс автоматизированной проверки кода);
   - предмет исследования (методы интеграции LLM в pipeline проверки кода с устранением галлюцинаций);
   - цель работы;
   - задачи (5–7 пунктов);
   - методы исследования (системный анализ, эксперимент A/B, статическая оценка качества кода, нагрузочное тестирование sandbox);
   - на защиту выносятся (3–5 положений);
   - апробация (если есть — публикации/выступления; иначе пропусти раздел);

11. **Глава 3. Программная реализация** (15–25 стр.):
    - 3.1. Реализация модуля `sandbox`:
      - Hardening-флаги `docker run`: `--network=none`, `--read-only`, `--cap-drop=ALL`, `--tmpfs /tmp:rw,noexec,nosuid,nodev,size=128m`, `--pids-limit=64`, `--security-opt=no-new-privileges:true`, `--stop-timeout=0`, `-m`, `--cpus`.
      - Watchdog hard-timeout: `ScheduledExecutorService.schedule(() -> docker kill -s SIGKILL, timeoutSeconds*1000ms)`; страховка через `docker wait` с `waitFor(timeoutSeconds + 2s)`.
      - Resolveolution verdict-а: приоритет `timedOut → TLE` раньше `exitCode == 137 → MLE` (иначе SIGKILL по timeout уезжает в MLE).
      - Сбор peak memory: оборачиваем команду так, чтобы контейнер перед exit писал `/sys/fs/cgroup/memory.peak` (v2) / `memory.max_usage_in_bytes` (v1) в `/app/.peak_memory_bytes`; параллельно polling `docker stats` каждые 100 мс через ScheduledExecutor; финал = `maxOf(polledPeak, cgroupPeak)`. Аргументация: для программ <500 мс polling пропускает peak, для долгих — cgroup-файл может не успеть быть записан при SIGKILL.
      - Поддерживаемые языки: Java (eclipse-temurin:21-jdk-alpine), Python (python:3.11-alpine). Kotlin исключён из MVP (см. п. 3.6).
    - 3.2. Реализация модуля `ai-analyzer`:
      - `AnalyzerPrompts.userPromptFull` — сборка user-message из 4 блоков с порядком: язык → описание задачи → результат sandbox → AST_FACTS → код в sentinel'ах.
      - `GigaChatClient` — OAuth2 client_credentials flow, обновление access-token, retry 3× на 5xx с jitter.
      - `GigaChatAnalyzer.callAndParse` — построение prompt, schema-validation, fallback.
      - `SchemaValidator` — JSON Schema Draft 7 (`explanation.json`); `additionalProperties=false` ловит инъецированные ключи; out-of-range на `codeQuality`.
      - `InputSanitizer` — нормализация Unicode NFKC, удаление управляющих/bidi/zero-width символов; ограничение длины кода 16 КБ; output-санитайзер (удаление HTML-тегов, опасных URL-схем).
      - `mapPayload` с verdict-guard cap'ами.
      - Caffeine cache key включает code+language+verdict-fingerprint+taskDescription+promptVariant.
    - 3.3. Реализация AST-экстрактора:
      - `AstFact`: `language`, `hasLoop`, `hasRecursion`, `hasComparison`, `cyclomaticComplexity`, `methodCount`, `maxNestingDepth`, `suspiciousReturnsConstant`, `lineCount`. Сериализация в JSON для prompt.
      - `JavaAstAnalyzer` — JavaParser 3.26 (CompilationUnit, AST visitor).
      - `PythonRegexAnalyzer` — regex-based (нет встроенного AST для Python в JVM); упрощённое выделение определений функций, циклов, рекурсии.
      - `AstMetricsService` — диспетчер по языку, безопасный wrapper (любая ошибка → `AstFact.empty(language)`).
    - 3.4. Реализация модулей `worker` и `task-resolver`:
      - Kafka producer/consumer (Spring Kafka, `KafkaTemplate`, `@KafkaListener`).
      - `WorkerService.processTask`: прогон тестов, агрегация passed/total, построение `AnalyzeContext` (с описанием задачи, verdict, первой ошибкой).
      - Early-stop: при первом неудачном тесте остальные помечаются SKIPPED — экономия времени для пользователя.
      - Сохранение `TaskResultEntity` + `AIAnalysisEntity` с FK.
    - 3.5. Реализация фронтенда:
      - Vite 5 + React 18 + TypeScript 5.3.
      - Роутинг (Login, Register, Dashboard, TaskList, TaskDetail, Submission, Submissions, Statistics, Results).
      - Monaco-редактор: настройка theme, language (java/python), live-completions.
      - Polling submissions: setInterval 2 с, остановка при `status ∈ {SUCCESS, FAILED, ERROR, PARTIAL_SUCCESS}`.
      - Zustand store для auth-токенов; refresh-перехватчик в axios-инстансе.
    - 3.6. Решения по MVP-границам (что вычеркнуто и почему):
      - Kotlin как пользовательский язык исключён (cold start `kotlinc` > 10 с → TLE на компиляции). Бэкенд возвращает 400, фронт не предлагает в селекторе. Sandbox-код для Kotlin сохранён (восстановим при наличии pre-built builder-image).
      - Scenario tests — реализованы только в задней частии sandbox, фронт пока не выводит детально (P2).
    - 3.7. Развёртывание. Docker compose (PostgreSQL 16, Kafka 7.5 + Zookeeper, MainApplication, Worker). Переменные окружения (.env): `JWT_SECRET`, `GIGACHAT_AUTH_KEY`, `GIGACHAT_AUTH_SCOPE=GIGACHAT_API_PERS`, `DB_*`.

## Часть 5. Стиль, тон, анти-плагиат

- Текст научный, нейтральный, без публицистики и эмоций. Никаких «революционный», «уникальный», «потрясающий».
- Никаких эмодзи в основном тексте и приложениях.
- От первого лица только в реферате и заключении: «в работе разработан…», «получены результаты…». В остальных главах — безличные обороты («предложен подход», «реализована подсистема»).
- Каждое утверждение, заимствованное из внешних источников, сопровождается ссылкой `[N]`.
- Каждый код-листинг сопровождается ссылкой на файл репозитория. Длинные методы (>60 строк) — разбивай на фрагменты с подписями «фрагмент 1 из 3».
- НЕ используй характерные обороты ИИ-сгенерированного текста: «давайте рассмотрим», «как мы можем видеть», «в итоге», «таким образом, мы получаем». Заменяй на «рассмотрим», «из приведённой таблицы следует», «итак».
- Не повторяй одну и ту же мысль в двух соседних абзацах. Не используй маркированные списки в местах, где уместен связный текст (особенно во введении и заключении).
- В каждой главе — 2–4 переходные фразы между подразделами, иначе текст распадается на конспект.
- Когда вводишь термин — дай определение в скобках или в сноске.
- Не используй прошедшее время разработки («мы разработали»). Используй настоящее («предложенная архитектура обеспечивает…»).

**Антиплагиат-гигиена.** Цитаты ≥ 25 слов оформляй кавычками и ссылкой `[N, c. M]`. Не копируй текст ГОСТов и документации Spring/Kotlin дословно — перефразируй с указанием источника.

## Часть 10. Жёсткие правила для исполняющей сессии

1. Прежде чем начать любую главу — выполни `Read` для каждого файла из списка в Части 4. Если файла нет — пометь раздел `{{TODO: <причина>}}` и продолжи дальше. Не выдумывай.
2. Когда упоминаешь метрику из A/B-эксперимента — открой соответствующий JSON в `experiment/results/<variant>/` и возьми число оттуда. В тексте формат: `B2 показал structural_valid_pct = 96.7 % против 88.3 % у baseline B1`.
3. Все ссылки на код в тексте — формата `листинг А.N` или `см. <имя класса>` (с пометкой в Приложении А).
4. Каждая глава начинается с короткого вводного абзаца («В настоящей главе…») и заканчивается выводом («Таким образом, …»).
5. После окончания первой полной черновой версии — прогнать всю работу через self-review:
   - проверка, что каждое число имеет источник;
   - удаление повторов, ИИ-канцелярита;
   - перепроверка ГОСТовских отступов и нумерации;
   - проверка, что все рисунки и таблицы пронумерованы и упомянуты в тексте.
6. В конце предложить Боссу 5 контрольных вопросов «что я пропустил» по содержанию (через `AskUserQuestion`). Только после ответа — финальная сборка `.docx`.
7. Не вставлять в `.docx` дословные фрагменты этого промпта.
8. Финальный артефакт — `thesis/build/Рысаев_А_И_ДИР_2026.docx`. Параллельно — единый `thesis/build/full.md` (исходник для конвертации).
